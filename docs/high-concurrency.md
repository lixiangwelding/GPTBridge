# 高并发扩容与验收

范围：当前个人MCP工作区。已测实机为10核Apple M4、16GiB内存。执行许可不等于吞吐倍数；同一源码写入仍受互斥锁保护。

## performance配置

| 容量 | 原值 | 高并发值 |
|---|---:|---:|
| 执行中的命令（含构建） | 8 | 64 |
| 其中重构建 | 2 | 4 |
| 排队+执行作业总数 | 32 | 256 |
| HTTP在途请求 | 32 | 256 |
| 其中长等待请求 | 24 | 192 |
| HTTP控制专用容量 | 未独立隔离 | 32 |
| stdio线程（含控制） | 4 | 32 |
| 其中stdio控制线程 | 未独立隔离 | 4 |
| stdio排队请求 | 32 | 256（224普通+32控制） |
| Unix进程文件句柄软预算 | 实测256 | 请求4096，受系统硬限额约束 |

模板：config/concurrency-performance.json。真正生效文件为server_info.concurrency.configuration_path返回的本机路径；不修改OAuth profiles.json。未配置的工作区仍使用保守默认。

## 行为边界

所有执行器从同一工作区状态目录加载已校验配置。配置变更需要排空后协调重启，旧server发现配置漂移拒绝新作业，但保留原request_id回执查询。数值范围有硬边界；非法、未知字段、超16KiB或符号链接配置均拒绝。

没有放开源码写锁、没有改slot锁算法、没有取消原输出资源锁；没有调整SQLite FULL持久化、自动重放unknown任务、删除历史或关闭权限检查。HTTP及stdio均预留控制处理容量，stdio输入不因普通队列满而堵塞，超额请求返回未执行的明确错误。

64个并行命令主要服务于独立I/O/读任务；重构建作为64中的子配额限4。16GiB机器不宜把几十个JVM/编译器同时放开。不同编译输出需声明独立resources；同一源码写入仍串行。

## 真实压测

1. 96个隔离实际worker任务，观察到64同时运行：约1251ms达到目标，约3313ms全部完成，重复执行0。8个独立build任务观察到4同时执行，全部完成。
2. 256条有活跃锁的排队记录占满后，第257项返回QUEUE_FULL，不错误回收活跃作业，不启动额外命令。
3. 192个真实HTTP请求同时长等待时，查询、溢出检查和取消合计约11ms；普通业务许可占满时server_info仍可响应。
4. stdio一次送入300个长等待请求，保留控制线程，控制响应约17ms，48项明确过载拒绝；总共302个唯一回执，无缺失、无重复。

上述耗时为一次隔离测试样本，不是生产延迟承诺。测试用轻量命令验证许可和调度，不冒称64个重计算业务吞吐。

首轮192个TCP连接同时建立时，仅128个进入HTTP层、64个被OS重置；实测kern.ipc.somaxconn=128。验收改为每批32个建连并保持先前请求等待，最终仍有192同时在途。未改系统全局TCP参数，未声称解决无限瞬时新连接洪峰。
